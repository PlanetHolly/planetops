How We're Organized

We built our Claude setup as we went. Now that all three of us use it, we need one clear picture of what's shared, what's private, and what stays on your own machine — so nobody overwrites anyone, and the next tool we add doesn't trip the same wire the checkpoint skill just did.

The one rule everything follows

The shared folder holds the logic everyone shares.
Memory, state, credentials, and settings stay on each person's own machine.

Jean said it exactly right in his note. The rest of this page is just that one sentence, drawn out so it's obvious where any new file, skill, or memory belongs.

The Three Places Things Live

Every file in our world sits in exactly one of three buckets. The trick is that two of them are in Dropbox and one is not — and being in Dropbox does not mean "shared."

1 · Shared Logic

~/Dropbox/PlanetApparel/ SyncedShared · all 3
  • Skills (the _Skills/ folder)
  • Pricing, PlanetIQ, client work, processes
  • Project notes, references, templates
  • The company "brain" any Claude can read

2 · Private Vault

~/Dropbox/Claude_Holly/
Claude_Kelly/ · Claude_Jean/ SyncedPrivate · just you
  • Your sensitive thinking
  • Pay, performance, personal notes
  • Your own project drafts
  • In Dropbox for backup — never shared with the others

3 · Machine-Local

~/.claude/ (your laptop only) Not syncedNever leaves machine
  • Claude's memory of you
  • Skill state & tracking files
  • Credentials / API keys
  • Settings & hooks

The one that surprises people: your private vault is in Dropbox, but Dropbox only syncs it back to your own account — it is not in the shared folder, so Kelly and Jean never see it. "In Dropbox" and "shared" are two different things.

Where Memory Lives — and Whose It Is

This was the heart of Jean's question. The answer: memory is per-person and stays on each machine. It is not shared, and that is correct — not a bug.

  • Your Claude's memory lives at ~/.claude/projects/…/memory/ on your own laptop. When you tell Claude "I prefer terse answers" or "I'm the CFO," that's saved there — only your Claude knows it.
  • Holly's Claude knows Holly's context. Kelly's knows Kelly's. Jean's knows Jean's. They don't bleed into each other.
  • Shared knowledge — facts about the company, pricing, processes, a project's status — does not go in personal memory. It goes in a document inside PlanetApparel/, where any of our Claudes can read it.

Rule of thumb: a fact about you → personal memory (local). A fact about the company → a shared doc in PlanetApparel/.

Whose Memory Is It? — Automatic

You never have to tell Claude "save this as mine." Identity is settled before you type a word — for two reasons:

  • The machine is the boundary. Your memory lives on your own laptop and is never synced. When Kelly opens Claude on Kelly's machine, the only memory it can touch is Kelly's — it physically cannot reach Holly's, because Holly's memory exists only on Holly's laptop. No shared pool to misfile into.
  • Skills detect you automatically. Any skill that needs "your vault" runs whoami first and routes to that person's folders. On Kelly's machine that's Claude_Kelly, on Jean's it's Claude_Jean — no declaration needed.

The only thing that needs a decision is personal vs. shared — and that's about the content, not whose: "I prefer short answers" is personal (auto-saved locally); "our bandana COGS is ~$1/unit" is a company fact that belongs in a shared PlanetApparel/ doc.

The catch: this only stays automatic for skills written the right way. A skill that hardcodes a path instead of using whoami will misroute no matter who's logged in — exactly the checkpoint bug above. That's what the "every new skill" rule protects.

Where Obsidian Fits

Obsidian is just a nicer window onto the same Dropbox folders — it doesn't add a fourth bucket and it has nothing to do with Claude's memory.

  • When you open Claude_Holly/ in Obsidian, you're looking at your private vault (bucket 2).
  • The PlanetApparel/Projects/ notes are shared project state (bucket 1) — the same files Claude reads.
  • Obsidian notes are documents. Claude's memory is separate plumbing under ~/.claude/. Editing a note in Obsidian never touches Claude's memory, and vice-versa.

The Trap We Just Hit — The Symlink

Here's the wire the checkpoint skill tripped, and why it matters for everything we build next.

To share skills, each machine has a shortcut (a "symlink") at ~/.claude/skills that points into the shared Dropbox folder. That's how all three of us run the same /build-doc, /today, etc. Good design.

But it has a hidden edge: anything a skill writes inside its own folder lands in shared Dropbox — even when the code looks like it's writing to your private ~/.claude/.

What the code looked like it wrote to: ~/.claude/skills/checkpoint/state/processed.log │ │ ← this is a shortcut (symlink) ▼ Where it actually wrote to: ~/Dropbox/PlanetApparel/_Skills/checkpoint/state/... ← SHARED with everyone

The checkpoint skill — the one that saves what each session worked on — kept its tracking ledger there. So it became one file all three of us would share, holding only Holly's sessions. If Kelly or Jean had turned it on as-is:

  • Dropbox "conflicted copy" fights over a file Holly's memory leans on,
  • everyone's sessions bleeding into one ledger, and
  • each other's old sessions wrongly flagged as "crashed."

Fixed as of 2026-05-29. The checkpoint skill's tracking file now lives at ~/.claude/checkpoint-state/ — outside the shortcut, on each machine. The skill also now detects who's running it (whoami) and uses that person's folders. Holly's 6 sessions were migrated with nothing lost; her setup behaves identically. Kelly and Jean can now safely turn it on. The shared _Skills/checkpoint/ folder now holds only logic — no state.

The Rule for Every New Skill

So this never happens again, every skill we add or share gets checked against three questions:

  • Logic → shared. The SKILL.md instructions and scripts go in _Skills/. Everyone runs the same logic.
  • State, ledgers, memory → local. Anything the skill writes and tracks over time goes to a machine-local path like ~/.claude/<skill>-state/ — never inside the skill's own folder (that's the symlink trap).
  • Person-specific paths → detect the user. If a skill needs "your vault" or "your folder," it resolves the current user with whoami (the way file-organization and /ss already do) — never hardcodes one person.

Quick test before sharing a skill: "If Kelly runs this, does it write to Holly's stuff or fight over a shared file?" If yes, its state isn't local yet.

Two Terminals, One Project

Holly hit this directly: open two Claude windows on the same project and they can overwrite each other's memory or notes. Two reasons, two fixes.

SituationWhat happensWhat to do
Two windows on the same machine, both saving memoryLast one to write wins — the other's update is clobberedLet one finish its save / checkpoint before kicking off the other. Don't run parallel sessions both editing memory.
Two people editing the same shared doc at onceDropbox makes a "(Conflicted copy)" — Holly resolves by handFor a big edit, say so in chat: "rewriting Pricing/x.md for the next hour." (Already in the shared CLAUDE.md conflict rules.)
Renaming or moving a shared folderLinks, references, and CLAUDE.md paths break for everyoneCoordinate first. Folder structure changes happen on purpose, not by accident.

Personal memory is safe across machines because it's local — Holly's and Jean's never collide. The only real overwrite risk is two windows on the same machine, or two people in the same shared file.
